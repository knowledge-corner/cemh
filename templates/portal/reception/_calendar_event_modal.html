{% comment %} The add/edit-event pop-up (FR-8, FR-9). One dialog whose fields follow the event type, rather than a separate pop-up per type. What reception is adding is a choice made *inside* the dialog — asking before it opens would mean knowing the answer to reach the question. A doctor gets the same dialog scoped to themselves: no event-type choice (always working hours) and no doctor picker (always their own), both left out of the markup entirely rather than merely hidden, so nothing about them is even submitted. Rendered into the page and hidden, not fetched: the form is small, and a dialog that needs a round trip before it appears is a dialog that sometimes does not. This dialog does need JavaScript to open, as the clinic's other modals do. The fallback is not a degraded version of this form — it is the Doctor schedule screen, which is plain HTML forms and can do everything here except in one step. The fields for the type not chosen are *disabled* as well as hidden, so a doctor half-filled-in before switching to Holiday is not submitted. "Last date" is two separate fields under the hood (holiday's own range, and the recurring booking's end date) — see CalendarEventForm — so only one is ever shown at once. There is no cabin field. Which room a booking gets is worked out once the dates and time are known — see appointments.calendar.allocate_cabins — so asking reception to pick one here would be asking them to already know the answer this form exists to work out. The same dialog edits one existing row, opened by clicking its own Edit button rather than a day cell — calendar.js repoints the form at reception_edit_calendar_event and pre-fills it, and hides the Recurring section entirely: editing changes the one occurrence that was clicked, never the pattern that generated it. A conflict on save reopens this exact state — see calendar_view's "pending_event_conflict" / "pending_event_pk" handling — with editing_pk telling the template which action the form posts back to. A submission with conflicting dates does not fail outright. It is held — see calendar_view's "pending_event_conflict" handling — and this pop-up is reopened exactly as it was left, values intact, underneath the Conflict Detected dialog below. "Skip Conflicting Dates" resubmits this same form with that choice made; "Redo Schedule" simply closes the dialog, leaving the form open to edit. {% endcomment %}
