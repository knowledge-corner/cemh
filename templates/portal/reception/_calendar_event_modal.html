{% comment %} The add-event pop-up (FR-8, FR-9). One dialog whose fields follow the event type, rather than a separate pop-up per type. What reception is adding is a choice made *inside* the dialog — asking before it opens would mean knowing the answer to reach the question. Rendered into the page and hidden, not fetched: the form is small, and a dialog that needs a round trip before it appears is a dialog that sometimes does not. This dialog does need JavaScript to open, as the clinic's other modals do. The fallback is not a degraded version of this form — it is the Doctor schedule screen, which is plain HTML forms and can do everything here except in one step. The fields for the type not chosen are *disabled* as well as hidden, so a doctor half-filled-in before switching to Holiday is not submitted. "Last date" is two separate fields under the hood (holiday's own range, and the recurring booking's end date) — see CalendarEventForm — so only one is ever shown at once. There is no cabin field. Which room a booking gets is worked out once the dates and time are known — see appointments.calendar.allocate_cabins — so asking reception to pick one here would be asking them to already know the answer this form exists to work out. {% endcomment %}
